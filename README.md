# configure-env

Configure, check and edit env files from a schema, interactively or in CI.

## Status

Pre-release; the package is not on npm yet. `apply` and `check` work; the other commands are being built.

The CLI reads a JSON schema that lists the env files (their paths and write policies) and the variables (names, types and validation rules), then works from it:

| Command    | Purpose                                            |
| ---------- | -------------------------------------------------- |
| `apply`    | write the env files the schema describes           |
| `check`    | change nothing; report drift and exit 1 when found |
| `init`     | start a schema for a project                       |
| `set`      | set one variable                                   |
| `get`      | print one variable                                 |
| `unset`    | remove one variable                                |
| `list`     | list the variables and where they are set          |
| `validate` | validate the values against the schema             |

Each command runs as an interactive TUI for people, or with `--ci` for unattended runs. Once published, it will run without installing:

```sh
npx @elvisgastelum/configure-env apply
```

## Schema (v1)

A project describes its env files in `env.schema.json` at its root. The format is versioned; this is version 1.

```json
{
  "$schema": "https://raw.githubusercontent.com/elvisgastelum/configure-env/main/schema/env.schema.v1.json",
  "version": 1,
  "variables": {
    "WEB_HOST": {
      "type": "host",
      "description": "Address the site is published on",
      "group": "Server",
      "default": "127.0.0.1",
      "required": true,
      "example": "192.168.1.115"
    },
    "WEB_PORT": { "type": "port", "default": 8080 },
    "API_TOKEN": { "type": "string", "secret": true, "minLength": 20 },
    "MODE": { "type": "enum", "values": ["dev", "prod"], "default": "dev" }
  },
  "files": [
    { "path": ".env.example", "policy": "merge", "variables": "*" },
    {
      "path": "deploy/.env.production.example",
      "policy": "generate",
      "header": "Generated by configure-env",
      "variables": ["WEB_HOST", "WEB_PORT"],
      "values": { "WEB_HOST": "192.168.1.<CT ID>" }
    },
    { "path": ".env", "policy": "create-only", "mode": "600", "variables": "*" }
  ]
}
```

[`examples/portfolio.env.schema.json`](examples/portfolio.env.schema.json) is a complete schema: the env setup of elvisgastelum.com.

Every object is strict: an unknown or misspelled key is an error, not ignored. The top level holds only `$schema`, `version` (must be `1`), `variables` and `files`.

### Variables

`variables` maps each name to its spec. A name matches `^[A-Za-z_][A-Za-z0-9_]*$`.

| Field         | Type    | Meaning                                                                             |
| ------------- | ------- | ----------------------------------------------------------------------------------- |
| `type`        | string  | one of the types below; required                                                    |
| `description` | string  | what the variable is for                                                            |
| `group`       | string  | a heading that groups related variables                                             |
| `required`    | boolean | the variable must be set; default `false`                                           |
| `allowEmpty`  | boolean | an empty value is accepted; default `true` when not required, `false` when required |
| `default`     | typed   | the value used when none is given; it must pass the variable's own rules            |
| `example`     | typed   | a sample value shown to people; it must pass the variable's own rules too           |
| `secret`      | boolean | mask the value in output (`••••` and the last 2 characters past 8); default `false` |
| `comment`     | string  | written as `#` lines above the key in generated files; `\n` starts a new line       |

`default` and `example` take the type's JSON type: a number for `number`, `integer` and `port`, a boolean for `boolean`, a string for the rest.

| Type      | Accepts                                                                    | Options                                               |
| --------- | -------------------------------------------------------------------------- | ----------------------------------------------------- |
| `string`  | any text                                                                   | `minLength`, `maxLength`, `pattern`, `patternMessage` |
| `number`  | a decimal number, like `0.5` or `1e3`                                      | `min`, `max`                                          |
| `integer` | a whole number                                                             | `min`, `max`                                          |
| `boolean` | `true`/`false`, `1`/`0`, `yes`/`no`, `on`/`off`; written as `true`/`false` | none                                                  |
| `enum`    | one of `values`, matched case-sensitively                                  | `values` (required)                                   |
| `email`   | an email address                                                           | none                                                  |
| `url`     | an absolute URL                                                            | `protocols`, like `["https"]`; any scheme when absent |
| `host`    | a hostname, or an IPv4 or IPv6 address                                     | none                                                  |
| `ipv4`    | an IPv4 address                                                            | none                                                  |
| `port`    | a whole number from 1 to 65535                                             | none                                                  |

`pattern` is a JavaScript regular expression in Unicode mode; `patternMessage` replaces the default error when a value does not match. An option of another type (say `minLength` on a `port`) is an error.

### Files

`files` lists the env files, in the order the tool handles them.

| Field         | Type          | Meaning                                                                                        |
| ------------- | ------------- | ---------------------------------------------------------------------------------------------- |
| `path`        | string        | relative to the project root, with `/`; no absolute paths, `..`, `.` or empty segments; unique |
| `policy`      | string        | `generate`, `merge` or `create-only` (below); required                                         |
| `variables`   | `"*"` or list | `"*"` for every variable in declaration order, or declared names in output order; required     |
| `mode`        | string        | the permissions as three octal digits, like `"600"`                                            |
| `header`      | string        | written as `#` lines at the top of the file                                                    |
| `values`      | object        | literal values for this file only, like placeholders in an example; written as is, not type-checked, no line breaks |
| `comments`    | object        | comments for this file only, replacing the variables' own `comment`; for this file's variables only |
| `description` | string        | what the file is for                                                                           |

| Policy        | What the tool does with the file                                              |
| ------------- | ----------------------------------------------------------------------------- |
| `generate`    | owns it: writes the whole file and rewrites it whenever it differs            |
| `merge`       | appends the keys it lacks, with their comments, and keeps every existing line |
| `create-only` | writes it only when it does not exist, then never touches it                  |

### How files are written

A generated or created file holds the `header` as `#` lines, a blank line, then each variable in the file's order: its comment as `#` lines, then `KEY=value`. A blank line separates blocks; a new block starts where the `group` changes or a variable has a comment. The value is the file's `values` entry, else the given value, else the `default`, else empty.

A `merge` file keeps every existing line byte for byte, including its line endings, `export` prefixes, quotes and comments; the missing keys go at the end after a blank line, with their comments. Existing values are never changed.

Values are written plain when they can be. A value holding whitespace, `#` or quotes is double-quoted with backslash escapes. A value holding `$` is single-quoted, so Docker Compose and dotenv-expand do not interpolate it: `PASSWORD='pa$$word'`. When it also holds a single quote or a line break, it is double-quoted with `$` written as `\$`.

A file path that leaves the project root, directly or through a symlinked directory, is refused, and so is writing through a symlink. Each file is written atomically (a temporary file in the same directory, flushed, then renamed into place) with the schema's `mode`, else the existing file's mode, else `644`. A new file never replaces one that appeared after planning: it is hard-linked into place, or, on a file system without hard links, created exclusively. A generate or merge file whose mode differs from the schema's `mode` is rewritten with that mode.

A line that is not a valid entry, such as a quote that is never closed, is kept as is and reported by `check`; the lines after it parse on their own.

The loader accepts a schema file saved with a UTF-8 byte order mark. A `host` whose last label is all digits must be a valid IPv4 address, so `999.1.1.1` is rejected.

### Editor support

The `$schema` line points editors such as VS Code at [`schema/env.schema.v1.json`](schema/env.schema.v1.json), which gives completion, hover docs and inline errors while editing. The JSON Schema checks the shape; the loader also checks what JSON Schema cannot express: defaults and examples against their type's rules, variable names in `files`, value overrides, and unique paths.

The JSON Schema is generated from the zod definition in `src/schema/definition.ts`. After changing the definition, run `pnpm schema:generate` and commit the result; a test and CI (`pnpm schema:check`) fail while it is stale.

## Usage

```sh
configure-env [command] [options]
```

Until the package is published, run it from a checkout with `pnpm start -- <command> [options]`; `--root` points it at a project.

| Command | What it does                                                         |
| ------- | -------------------------------------------------------------------- |
| `apply` | writes the env files the schema describes; the default command       |
| `check` | changes nothing; reports drift and invalid values, exits 1 on either |

`configure-env <command> --help` shows each command's options and examples.

### Global options

| Option            | Meaning                                                                       |
| ----------------- | ----------------------------------------------------------------------------- |
| `--schema <path>` | the schema file; default `env.schema.json` in the root                        |
| `--root <dir>`    | the project root; default where the command was typed (`INIT_CWD`, else cwd)  |
| `--file <path>`   | only this schema file; repeat it for more                                     |
| `--ci`            | never prompt; also when the `CI` environment variable is set (not `false`/`0`) |
| `--json`          | print one JSON document on stdout, logs on stderr; implies no prompts         |
| `--no-color`      | plain output; `NO_COLOR` is honoured too                                      |
| `-h`, `--help`    | the help, of the CLI or of a command                                          |
| `-v`, `--version` | the version                                                                   |

A missing schema exits 2 with a hint to run `configure-env init`; an invalid one exits 1 and names each problem.

### apply

In a terminal, `apply` shows the schema files with their policy and current state and asks which to write. It then prompts, grouped by `group`, for the values the chosen files need: every variable of a generate file or a file it creates, and the keys a merge file lacks. A variable a file sets through `values` is not asked for. Each prompt fits the type: a select for an `enum`, a yes/no for a `boolean`, a hidden input for a `secret`, and text for the rest, starting from the default and checked against the variable's rules. It shows the plan (secrets masked), asks before writing, and writes. Ctrl-C at any prompt exits 130 and writes nothing. A create-only file that exists is skipped; a refused path is reported with its reason.

With `--ci`, or `CI=true`, it never prompts. Each value comes from `--set KEY=VALUE`, else the environment variable of the same name (when not empty), else the schema default. A required variable that ends up with no value, or any invalid value, is an error: nothing is written and it exits 1. It prints one line per file:

```text
config/app.env: created
.env.example: added keys: WEB_PORT
.env: skipped (exists)
```

Other states are `updated`, `unchanged`, `skipped (refused: <reason>)` and `failed (<reason>)`. Without a terminal and without `--ci` it exits 2.

```sh
configure-env apply
configure-env apply --ci --set WEB_PORT=9090
WEB_HOST=10.0.0.5 configure-env apply --ci --file .env
configure-env apply --ci --json
```

### check

`check` writes nothing. Per file it reports a missing file, a generated file that differs from the schema, the keys a merge file lacks, a mode other than the schema's `mode` (`mode 644, expected 600`), values that break their variable's rules (secrets masked), and lines that are not valid entries. It exits 1 when it finds any, 0 when everything is current. Generated files are compared with the values from `--set` and the environment, as `apply --ci` writes them. It runs the same way with or without a terminal.

```sh
configure-env check
configure-env check --ci --json
```

### JSON output

With `--json`, `apply` prints `{ "command": "apply", "ok", "errors", "files" }`; each file has `path`, `policy`, `action`, `status` (the line above), `addedKeys` and `written`. `check` prints `{ "command": "check", "ok", "drift", "errors", "files" }`; each file has `path`, `policy`, `status`, `drift`, `missingKeys`, `invalid` (`key`, `message` and the masked `shown` value), `invalidLines`, and `mode` when it differs.

### Exit codes

| Code  | Meaning                                                                  |
| ----- | ------------------------------------------------------------------------ |
| `0`   | ok                                                                       |
| `1`   | drift, an invalid value or schema, or a failed write                     |
| `2`   | usage error: a bad option, no schema, or no terminal without `--ci`      |
| `130` | cancelled                                                                |

### Example schema

[`examples/portfolio.env.schema.json`](examples/portfolio.env.schema.json) is the env setup of [elvisgastelum.com](https://github.com/elvisgastelum/elvisgastelum.com), the project this tool was extracted from:

```sh
pnpm start -- apply --ci --schema examples/portfolio.env.schema.json --root ../my-project
```

## Development

Requirements: Node.js 22 or later (see `.node-version`) and pnpm 12 (pinned in `package.json` through `packageManager`; `corepack enable` provides it).

| Script                 | What it does                                 |
| ---------------------- | -------------------------------------------- |
| `pnpm dev`             | run the CLI from source with tsx             |
| `pnpm start`           | same as `pnpm dev`                           |
| `pnpm lint`            | lint with ESLint                             |
| `pnpm format`          | format with Prettier                         |
| `pnpm format:check`    | check the formatting without changing files  |
| `pnpm typecheck`       | type-check with `tsc`                        |
| `pnpm test`            | run the tests with Vitest                    |
| `pnpm schema:generate` | regenerate `schema/env.schema.v1.json`       |
| `pnpm schema:check`    | fail when the committed JSON Schema is stale |

CI runs lint, format:check, typecheck, schema:check and test on every pull request and on every push to `main`.
